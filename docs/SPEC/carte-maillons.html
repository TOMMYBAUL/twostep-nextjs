Two-Step — Carte des maillons du pipeline stock

De la caisse du marchand jusqu'au feed Google LFP. Le cœur du produit = la qualité de la donnée stock : propre, traçable, enrichie, affichée honnêtement. Chaque maillon a un contrat auditable dans docs/SPEC/.

North-star : « feed Google LFP as a service » — l'exactitude EST la promesse. Trois invariants transverses gravés dans le code : ne rien perdre en silence · zéro faux positif (mieux vaut null qu'une valeur fausse) · afficher honnêtement (jamais un faux « disponible » / « complet »).

Le flux de la donnée — du stock au feed

Lecture de gauche à droite. Chaque étape transforme la donnée et la passe à la suivante. Déplie « ⓘ détail » pour les invariants testés et les modes d'échec.

🏬 Le marchand

Caisse (API), export planifié, fichier, facture. « N'importe quelle caisse » — modèle NearSt, POS-agnostique.

▸
M1

Collecte

Capter le stock de n'importe quelle source, sans perte silencieuse.

✅ Construit + testé
POS pull (Square·Shopify·Lightspeed·Zettle·Clictill·Fastmag) Webhooks temps réel Push fichier CSV/XLSX (snapshot) Factures/scan — hors-cap
ⓘ détail
Invariants :
  • Catalogue fantôme bloqué (POS vide = blip → ne masque rien)
  • Source explicite + source_ts réel sur chaque écriture
  • Pagination complète (pas de troncature 1000 → doublons)
  • Nom seul jamais une identité
Dette : fuzzy nom à durcir hors POS · ambiguïté webhook (null) à trancher.
▸
M2

Identité

Décider qui est quoi : GTIN fort vs SKU interne vs rejet.

✅ Construit + testé
Checksum GTIN 8/12/13/14 UPC-12 → EAN-13 ISBN / CIP (médicaments FR) Match : posItem › EAN › SKU › nom
ⓘ détail
Invariants :
  • EAN faux checksum → traité en SKU, jamais en lookup GTIN
  • Nom seul jamais une identité (rejet motivé, listé)
  • Compteurs exacts : acceptés + rejetés = total
  • Index produits complet et paginé (anti-doublon)
▸
M3

Enrichissement

EAN → photo / marque / catégorie / nom, avec score de confiance.

✅ Unit testé🔑 e2e photo (env live)
Cascade : GS1 › KicksDB › OFF/OBF › Google PC › CLIP › BERT › EAN-Search Photo (vérif IA fail-closed) Marque (allow-list) Catégorie FR (allow-list)
masqué < 0.70
pending ≥ 0.70
validé ≥ 0.95
Le score décide de la visibilité feed. Garde de concordance D7 : EAN discordant → downgrade validé→pending.
ⓘ détail
Le maillon cassé au 1er test réel (27/06), corrigé (a→d) :
  • Vérif photo IA fail-closed (clé absente → image écartée, pas publiée)
  • Requête image n'utilise jamais l'EAN brut (= cause des 6/7 photos fausses)
  • Marque & catégorie : allow-list, inconnu → null (jamais inventer)
Trou de preuve : correctude photo sur vrais EAN = rapport validé par Thomas (env live requis).
▸
M4

Stockage

Écrire la quantité de façon atomique + réconcilier le snapshot.

✅ Construit + testé
updateStockAtomic (FOR UPDATE, ≥0) Anti-régression source_ts Réconciliation : disparu → 0 7 sources tracées
ⓘ détail
Invariants :
  • Atomicité (race TOCTOU éliminée, jamais de négatif)
  • Garde anti-push-partiel : couverture < 50% → skip + erreur visible
  • Write stock=0 toujours sous captureError (vendu non masqué = faux positif n°1)
Dette : seuil 50% codé en dur (à paramétrer) · pas de ledger multi-source.
▸
M5

Confiance

Traduire l'état DB en affichage honnête pour le consommateur.

✅ Construit + testé
États : disponible · probable · épuisé Fraîcheur = source_ts (pas updated_at) 24h realtime / 12h snapshot Signalements clients (≥1 probable, ≥3 out)
ⓘ détail
Invariant clé : un webhook traité avec 30h de retard dit « probable » (vérité), jamais « Disponible » (le mensonge d'updated_at). Source manual plafonnée à « probable » ; qty ≤ 2 → « probable ».
▸
M6

Sortie Google LFP

Émettre les produits éligibles vers Google, 2 canaux complémentaires.

✅ Code testé🔑 pilote live
Voie A — cron Merchant API Voie B — feed XML streamé Inventory push temps réel Readiness lfp_feed_ready
ⓘ détail
Invariants :
  • Gate d'éligibilité unique (GTIN + prix + image) partagé par les 3 sorties → 0 divergence
  • Promo honnête (émise ssi active & sale < base)
  • Dispo = chaîne exacte « in stock » (jamais « in_stock » = rejet silencieux)
  • Statut produit async (200 insert ≠ acceptation → quality_alerts)
Vrai blocage = 1 marchand pilote live, pas le code (Google a tout débloqué avril 2026).

Ce que fera Fable 5

Le dossier docs/SPEC/ est son référentiel : un contrat par maillon.

Phase 1 — AUDIT (les 7 maillons faits)
  • Pour chaque invariant du contrat : trouver le code, vérifier le test, tenter de le réfuter
  • Sortie par maillon : CONFORME / ÉCART (cas qui casse) / NON PROUVÉ
  • Chercher les chemins jumeaux qui contournent une garde (classe de bug déjà vue)
Phase 2 — BUILD (le code pur restant)
  • Chunk cron google-feed · preuve charge 10k→50k (M7)
  • Tests manquants + audit OAuth (M9) · fuzzy nom (M1/M2) · auth.getUser() (M8) · seuil couverture (M4)
  • Barre de preuve : test + preuve réelle inspectée ; 0 migration prod sans GO
